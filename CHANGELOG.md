# Changelog

All notable changes to `runfabric` are documented in this file.

The format is based on the policy in `CHANGELOG_POLICY.md` and follows Semantic Versioning in `VERSIONING.md`.

## [Unreleased]

### Added

- **Daemon: full engine surface** — `runfabricd` now exposes every daemon-shaped engine capability, closing the CLI↔daemon feature gap: `POST /invoke` (function or `workflow:<name>` target, JSON body payload), `POST /logs` (provider + local logs, one function or all), `POST /traces` (traces aggregated by service/stage), `POST /metrics/functions` (per-function provider metrics; the daemon's own Prometheus scrape stays on `GET /metrics`), `POST /doctor` (backend + provider readiness, best-effort per side), `POST /recover` (`mode=rollback|resume|inspect`, `dryRun=1` preview), `POST /fabric/health` + `POST /fabric/targets` (multi-cloud endpoint health and target list, completing the fabric trio), `POST /state/{list|pull|backup|restore|reconcile|migrate|unlock|lock-steal}` (state-backend operations; `out`/`file` paths are workspace-confined like `config`), `POST /workflow/{run|status|cancel|replay|runs}` (durable workflow runtime: start a journaled run with a JSON input body, poll/cancel/replay it by runId, list a stage's recent runs — new engine helper `WorkflowRuns` exposes the run store's listing), and `POST /router/{history|simulate|verify|shift|restore}` (sync history + analytics, local routing simulation, chaos failover verification, canary weight shift, snapshot restore — new engine helpers `RouterSimulateFromFabricState`/`RouterVerifyFailoverFromFabricState`/`RouterShiftFromFabricState`/`RouterHistoryFromFabricState`/`RouterRestoreFromSnapshot`). Every op runs on the serialized per-request-credential path (same `X-Provider-*`/`X-State-*`/`X-Router-*`/`X-Secret-*` semantics as deploy), and mutating ops (recover, state restore/reconcile/migrate/unlock/lock-steal, router shift/restore) invalidate the stage's response cache. Also fixed: `POST /releases/history` existed on the config API but was never forwarded by the daemon's outer mux — it is now reachable. daemon-client gains `invoke()`, `logs()`, `traces()`, `functionMetrics()`, `doctor()`, `recover()`, `fabricHealth()`, `fabricTargets()`, `releaseHistory()`, `stateOp(op, …)`, `routerOp(op, …)`, `workflowRun()/workflowStatus()/workflowCancel()/workflowReplay()/workflowRuns()`, op-specific `params`, and JSON body support (typed in `index.d.ts`).
- **Daemon multi-cloud deploy + router over it** — the daemon now speaks the framework's multi-cloud model end-to-end: `POST /deploy|/plan|/remove` accept a `provider` query param (a `providerOverrides` key — the CLI `--provider` equivalent, previously hardcoded empty on the daemon path); new `POST /fabric/deploy` deploys to EVERY `fabric.targets` provider and returns the fabric state with per-provider endpoints; new `POST /router/sync` (with `dryRun=1` preview) generates the multi-cloud routing config (failover/latency/round-robin) from fabric state and syncs it through the configured router plugin via the shared credentialed path (per-request headers, secret refs, same-cloud fallbacks). Both new ops serialize, take per-request credentials — one `X-Provider-*` group per target cloud in a single request — and invalidate the stage cache. daemon-client gains `fabricDeploy()`, `routerSync()`, and the `provider`/`dryRun` request fields. New app-level `RouterSyncFromFabricState` shared by daemon and future CLI callers.
- **Daemon telemetry** — `runfabricd` now correlates and measures every request: inbound W3C `traceparent` headers are honored, so a request from an upstream service joins its distributed trace instead of starting a new root (the trace id is echoed as `X-Trace-Id` and logged as `trace_id`); `X-Request-Id` is accepted or generated and echoed on responses (and attached to OTel spans), a structured JSON access log is emitted per API request (disable with `RUNFABRIC_DAEMON_ACCESS_LOG=0`), and `/metrics` gains operation-level series (`runfabric_daemon_operations_total{op,outcome}`, `runfabric_daemon_operation_duration_seconds{op}`), auth/rate-limit rejection counters (`runfabric_daemon_auth_rejections_total{reason}`), Redis API-cache hit/miss counters (`runfabric_daemon_cache_requests_total{endpoint,result}`), and process/runtime gauges plus `runfabric_build_info`.
- **Fixed: `aws-lambda` lifecycle/observability methods were stubs** — several `Provider` methods returned canned data instead of calling AWS; all now do real work (verified by a Floci-emulator integration test in `extensions/providers/aws-lambda/floci_test.go`, build tag `floci`, that drives the `Provider{}` contract directly):
  - **`Invoke`** echoed the request payload back as the result (so `runfabric invoke run` reported `{}` / the input, never calling the function). Now performs a real synchronous Lambda `Invoke` against `<service>-<stage>-<function>` and returns the actual response payload, surfacing a handled `FunctionError` as an error.
  - **`Remove`** was a **no-op that reported success while deleting nothing** — it leaked the Lambda, IAM role, function URL, and log groups on every `runfabric remove`. It now tears them all down (function URL → function → log group per function, then detaches policies and deletes the shared `runfabric-<service>-<stage>-exec` role), idempotently.
  - **`Logs`** returned the literal line "logs are available in CloudWatch"; now reads real CloudWatch `FilterLogEvents` for the function's log group (or aggregates all functions, prefixed).
  - **`FetchMetrics`** returned `"available-via-cloudwatch"`; now reads real CloudWatch `AWS/Lambda` statistics (invocations/errors/avg duration, last 1h) per function.
  - **`FetchTraces`** returned `"available-via-xray"`; now reads real X-Ray `GetTraceSummaries`, degrading gracefully (empty + message) where X-Ray is unavailable.
  - **Deploy now publishes immutable Lambda versions** and maintains a `live` alias pointing at the newest one, so deploys are addressable/rollback-able.
  - **`Recover`** returned canned acknowledgements; now inspects the real deployed state (Lambda `GetFunction` per configured function). `inspect` reports the snapshot; `resume` adds it as `ResumeData`; **`rollback` genuinely reverts** — it repoints the `live` alias to the previous published version per function (reporting each `N->M` transition), or reports "no earlier version".
  - **Step Functions orchestration** (`SyncOrchestrations`/`RemoveOrchestrations`/`InvokeOrchestration`/`InspectOrchestrations`) returned canned status; now real. On deploy, each workflow whose steps are all `code` steps bound to deployed functions is compiled to an Amazon States Language state machine (`<service>-<stage>-<workflow>`) chaining Lambda-invoke tasks — each with exponential-backoff `Retry` on transient faults and a `Catch` to a terminal fail state — backed by a generated Step Functions role. Workflows with AI/human-approval/unbound steps are skipped with a recorded reason (they run on the durable runtime). Invoke starts an execution, inspect lists machines + recent executions, and remove deletes them. Branching/parallel/map await a workflow-DSL extension (the config is linear today).
  - CLI gained `runfabric workflow approve`.
- **`gcp-functions` + `azure-functions` Floci integration tests + endpoint overrides** — extended the Floci provider-test pattern to two more clouds, each a `floci_test.go` (build tag `floci`) driving the provider's contract directly, plus the endpoint-override plumbing that makes it possible:
  - **GCP** — new `GCP_ENDPOINT_URL` rewrites every `*.googleapis.com` host (cloudfunctions, storage, logging, workflowexecutions, cloudtrace) to a local emulator, resolved at call time so production is untouched when unset. The test (`extensions/providers/gcp-functions/floci_test.go`) runs the honest lifecycle `floci-gcp` supports: GCS source upload → `Deploy` (Cloud Functions v2 create + LRO) → control-plane presence → `Remove` → gone. `floci-gcp` is control-plane only (no function runtime), so invoke/logs/metrics are out of scope there.
  - **Azure** — new `AZURE_ENDPOINT_URL` overrides the ARM management host (and data-plane app/SCM hosts) across deploy/remove/orchestration/invoke. The `floci_test.go` covers the ARM `Microsoft.Web/sites` control-plane lifecycle `Deploy` → `Remove` against `floci-az`.
  - **Fixed: Azure `Deploy` never pushed function code** (`_ = root`) — it created the resource-group + function-app shell but shipped no handler, so the app served nothing. `Deploy` now zips the project root and pushes it via **Kudu zip deploy** (best-effort: an emulator without Kudu is recorded as `code_deploy=skipped` rather than failing the deploy), emits real per-function invoke URLs (`<app>/api/<fn>`), and `Invoke` now prefers the function-specific URL. This real code-push → invoke path is verified end-to-end by `TestDeployPushesCodeAndInvokeReturnsPayload` against an ARM+Kudu+function `httptest` double (always-on) — `floci-az` can't validate it (no Kudu; its runtime image has no arm64 manifest).
  - `make test-floci` now covers all three providers; `make test-floci-{aws,gcp,az}` run one cloud at a time.
- **Provider endpoint overrides + mock lifecycle tests (7 REST providers)** — extended the "make the provider testable against a local double" work beyond the Floci clouds. Each REST-based provider that hardcoded a single cloud API host now honors a call-time `<PROVIDER>_ENDPOINT_URL` override (production is untouched when unset; existing host `var` test-seams are preserved as fallbacks), and gains a normal (untagged) `deploy_mock_test.go` that drives Deploy → Invoke → Remove through the provider's contract against a faithful `httptest` double (create/upload hit, override-based invoke URL emitted, Invoke returns the echoed payload, delete issued):
  - `cloudflare-workers` (`CLOUDFLARE_ENDPOINT_URL`), `alibaba-fc` (`ALIBABA_ENDPOINT_URL`), `digitalocean-functions` (`DIGITALOCEAN_ENDPOINT_URL`), `ibm-openwhisk` (`IBM_OPENWHISK_ENDPOINT_URL`), `fly-machines` (`FLY_ENDPOINT_URL`), `vercel` (`VERCEL_ENDPOINT_URL`), `netlify` (`NETLIFY_ENDPOINT_URL`).
  - **Not applied** to `linode` (deploy/remove/invoke are command/executor-driven via `exec.Command` — no HTTP host to point at a double; already has a `commandRunner` seam) or `kubernetes` (uses `client-go` against a `KUBECONFIG`-specified API server, which is itself the override; a real lifecycle test needs a local cluster à la kind). These are documented exclusions, not gaps.
  - Rationale: none of these clouds have a Floci emulator, so the override makes them mock-testable now and emulator/proxy-ready later, and the mock validates each provider's real REST deploy/invoke/remove wiring.
- **Workflow human-approval resume** — a paused `human-approval` step can now be resolved and the run resumed end-to-end: new engine helper `app.WorkflowApprove` (records the decision + reviewer via `ResolveApproval`, then `ResumeRun`; the step defaults to the run's paused step), daemon `POST /workflow/approve` (`decision=approve|reject`, optional `step`/`reviewer`), daemon-client `workflowApprove()`, and CLI `runfabric workflow approve --run-id <id> --decision approve|reject [--step] [--reviewer]`. Approve/reject both complete the gate (rejection is recorded on the step output, not a failure) so the workflow continues.
- **Framework E2E suite** — new black-box end-to-end tests under `platform/test/e2e` (build tag `e2e`, `make e2e`) drive the real `runfabric`/`runfabricd` binaries — CLI as a subprocess, daemon over HTTP — rather than in-process `app.*`. These provider-agnostic lanes cover the durable workflow lifecycle (run → pause → approve → resume, cancel, runs), config surface, and cross-cutting invariants (`X-Request-Id` echo, inbound `traceparent` join, config-path confinement, non-loopback bind refusal without `--api-key`, api-key enforcement). Provider-specific cloud tests (deploy → invoke → logs → remove, Step Functions, rollback) live with their provider — `extensions/providers/aws-lambda/floci_test.go` (build tag `floci`, `make test-floci`) — driven through the `Provider{}` contract against a [Floci](https://floci.io) emulator, so they travel with the provider on extraction.
- **CLI trace propagation** — `runfabric` and `runfabricw` now join a caller's distributed trace: the W3C `TRACEPARENT`/`TRACESTATE` environment variables (the otel-cli convention) are extracted at startup (`telemetry.ContextFromEnv`) and every invocation runs under a root span named after its subcommand (`runfabric deploy`, `runfabricw start`, …) that records the command error on failure. A CLI run spawned by an upstream service (e.g. a PaaS job processor) now maps end-to-end in the tracing backend instead of appearing as an untraceable orphan. Both binaries also flush spans on the error path now (exit is routed through the deferred telemetry shutdown, which `os.Exit` previously skipped).
- **Scoped AWS identities: deploy vs state vs secrets** — the s3/dynamodb state backends honor `RUNFABRIC_STATE_AWS_ACCESS_KEY_ID/_SECRET_ACCESS_KEY/_SESSION_TOKEN/_REGION` (daemon headers `X-State-Aws-*`) and the aws-sm plugin honors `RUNFABRIC_SM_AWS_*` (`X-Secret-Aws-*`), each winning over the AWS default chain when set and falling back cleanly when not (partial sets never form a static identity). The deploy target (`AWS_*` / `X-Provider-Aws-*`), the state store, and the secret source can now be three different AWS accounts in one operation, per request. New daemon-client helpers `stateAwsHeaders()` / `awsSecretManagerHeaders()`; contract regenerated.
- **Per-request router + Vault credentials on the daemon** — the daemon's per-request credential mechanism (previously providers `X-Provider-*` and state `X-State-*`) now also accepts a router group (`X-Router-Api-Token`, `X-Router-Zone-Id`, `X-Router-Account-Id` → `RUNFABRIC_ROUTER_*`) and a Vault secret-manager group (`X-Secret-Vault-Addr/-Token/-Namespace` → `VAULT_ADDR/VAULT_TOKEN/VAULT_NAMESPACE`), so a multi-tenant daemon can DNS-sync and resolve `vault://` refs with the calling project's identity instead of ambient env. Declarations live in `providerpolicy` (`RouterCredentialVars`, `SecretManagerCredentialVars`) and ship in the daemon-client `credentials.json` contract; new client helpers `routerHeaders()` / `vaultSecretManagerHeaders()`. Cloud secret managers (aws-sm/gcp-sm/azure-kv) intentionally reuse the matching `X-Provider-*` group.
- **Daemon lifecycle-op hardening** — deploy/remove/plan/releases/release-history now always serialize on one mutex (previously only credentialed deploy/remove): every one of these Bootstraps, which installs the process-global secret resolver and can mutate env (router token priming); concurrent ops could corrupt each other. Additionally, requests carrying any credential header bypass the shared Redis response cache in both directions — a tenant-specific plan/validate response is never stored for, or served to, another caller — while credentialed deploys still invalidate the stage's cache.
- **Daemon extension catalog** — new authorized `GET /extensions` on `runfabricd` returning every plugin kind (provider, router, secret-manager, state, runtime, simulator), the runfabric.yml key that selects it (`provider.name`, `extensions.routerPlugin`, `extensions.secretManagerPlugin`, `extensions.statePlugin`, …), defaults, and the plugins available to the daemon (built-ins merged with external plugins discovered under `RUNFABRIC_HOME/plugins/<kind>`). Lets dashboards/PaaS render the extension map without hardcoding framework knowledge.
- **daemon-client trace propagation** — `@runfabric/daemon-client` requests accept `traceparent`/`tracestate`/`requestId`; results return `traceId`/`requestId` (from the daemon's `X-Trace-Id`/`X-Request-Id` echo, with a traceparent-derived fallback against older daemons). New helpers `newTraceparent()` and `traceIdOf()`.
- **Router credentials via the secret subsystem on deploy** — the deploy pipeline (CLI *and* daemon `/deploy`) now primes `RUNFABRIC_ROUTER_API_TOKEN` from `extensions.router.credentials` before DNS sync: custom `apiTokenEnv`, then `apiTokenSecretRef` (resolved through the top-level `secrets:` map and, when `extensions.secretManagerPlugin` is set, secret-manager refs like `vault://`/`aws-sm://`), then `apiTokenFileEnv`. Previously only the `runfabric router` CLI commands primed the token, so daemon-driven deploys required a pre-exported env var. The primed token is restored/unset after the sync so it never lingers in the long-running daemon environment. The pipeline also now reads zone/account IDs from the policy's `zoneIDEnv`/`accountIDEnv` and honors the router policy's `dryRun` on auto-sync.
- **runfabric generate** — In-project scaffolding: `runfabric generate function <name>` with triggers http, cron, queue. Creates handler file and patches `runfabric.yml`; supports `--trigger`, `--route`, `--schedule`, `--queue-name`, `--dry-run`, `--force`, `--no-backup`.
- **configpatch** — Safe YAML patching in `engine/internal/configpatch` (add function with backup, collision detection, dry-run plan).
- **scaffold** — Shared handler templates and function-entry builder in `engine/internal/scaffold` for init and generate.
- Unit and integration tests for generate, configpatch, and scaffold (init-then-generate flow).
- **Phase 13 — Quality and DX:** Provider contract test and doc-sync (`engine/internal/deploy/api`: `APIProviderNames()`, doc_test.go; DEPLOY_PROVIDERS.md lists API-wired providers). `make check-syntax` for fast CI (vet + build + test without -race). `runfabric call-local --serve --watch` for file watch and reload (same as dev --watch). [TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md) with per-provider errors and fixes. Compose concurrency documented in COMMAND_REFERENCE. Code ownership in AGENTS.md. Real-deploy and unsafe-defaults rules in RUNFABRIC_YML_REFERENCE. `runfabric init --with-ci github-actions` adds `.github/workflows/deploy.yml`.
- **Build artifact cache** — Per-function content hash (config + handler + package.json/go.mod/requirements.txt) in `engine/internal/buildcache`; cache under `.runfabric/cache`. `runfabric build` reports cache hit/miss and stores hash; `--no-cache` forces rebuild.
- **Generate extensions** — `runfabric generate resource <name>` (resources.database|cache|queue), `generate addon <name>`, `generate provider-override <key>`; configpatch AddResource/AddAddon/AddProviderOverride and scaffold BuildResourceEntry/BuildAddonEntry/BuildProviderOverrideEntry.

### Removed

- **Legacy `state:` config block** — the pre-`backend.kind` state-engine block (`state.backend`/`state.local`/`state.postgres`/`state.s3`, local/postgres/s3 only) is gone from the config model and schema. It had no runtime consumers; `backend.kind` (all 7 kinds) and `extensions.statePlugin` are the selectors.
- **`GetSecret` wire-method compatibility** — the secret-manager plugin protocol is `ResolveSecret` only; the adapter fallback and the built-in plugins' `GetSecret` aliases are removed.

### Changed

- **Credential model: provider keys are the base identity; declarative same-cloud fallbacks** — provider credentials stay on their standard native names (`AWS_*`, `CLOUDFLARE_API_TOKEN`, …; deliberately NO `RUNFABRIC_PROVIDER_*` spelling), and dependent extensions fall back to them through a new declarative `fallback` field on credential declarations (`CredentialVar.Fallback` / plugin.yaml `fallback:` / contract `fallback`), resolved by the new `plugin-sdk provider.ResolveVar`. Router plugins now declare their chains as data sourced from the plugin packages: cloudflare `RUNFABRIC_ROUTER_API_TOKEN→CLOUDFLARE_API_TOKEN` (**behavior change**: previously the provider key was deliberately ignored), zone/account fall back to `CLOUDFLARE_ZONE_ID`/`CLOUDFLARE_ACCOUNT_ID`; ns1 `→NS1_API_KEY` and azure-tm `→AZURE_ACCESS_TOKEN` migrate from hardcoded chains to declarations. Router-specific values (env, token file, daemon `X-Router-*` headers, `apiTokenSecretRef`) always beat the fallback. Fallback keys are validated at plugin load, pinned by the plugin.yaml sync tests, shipped in the daemon-client contract, and surfaced by `GET /extensions` (whose plugin payloads now include `credentials` for routers and secret managers too). Multi-cloud PaaS deploys can forward several provider groups in one daemon request (e.g. `X-Provider-Aws-*` + `X-Provider-Cloudflare-Api-Token`) so the router fallback resolves with tenant credentials.
- **Scoped env spellings for non-provider kinds** — declared state/secret-manager/router vars whose native names are not already RunFabric-namespaced can also be supplied as `RUNFABRIC_STATE_<KEY>` (e.g. `RUNFABRIC_STATE_AZURE_STORAGE_KEY`), `RUNFABRIC_SM_<KEY>` (e.g. `RUNFABRIC_SM_VAULT_TOKEN`), and `RUNFABRIC_ROUTER_<KEY>`; Bootstrap resolves them into the native var (mirrors follow), and the native var always wins so per-request daemon credentials stay authoritative.
- **Credential declarations validated at plugin load** — external plugin.yaml `credentials:` blocks are now validated when the plugin is discovered/installed (`manifests.ValidateCredentialSpecs`): env keys must be `UPPER_SNAKE`, headers must be well-formed `X-*`, no duplicate env keys or headers within a plugin, and mirrors must be distinct real env keys that don't collide with declared ones. A malformed block rejects the plugin into the Invalid report with a clear reason instead of surfacing later as a broken credential group. The same rules are enforced on every built-in declaration (all extension kinds) by test.
- **Extension credential audit: every in-tree plugin declares, loads, and validates** — the linode external provider now declares `LINODE_TOKEN` (it read the var but declared nothing); gcp-secret-manager and azure-key-vault-secret-manager declare their env-only addressing vars (`GCP_PROJECT_ID`/`GOOGLE_CLOUD_PROJECT`, `AZURE_KEY_VAULT_NAME`) in Go + plugin.yaml (auth stays on the cloud's ambient identity). Pin tests are now filesystem/ID-driven instead of hardcoded plugin lists (states, routers, runtimes, simulators — declaration-less kinds like local/sqlite are automatically pinned to declare none), and a new tree-wide sweep validates EVERY `extensions/**/plugin.yaml` credentials block against the load-time shape rules — including separate-module plugins with no in-engine Go declaration.
- **plugin.yaml credential declarations pinned repo-wide** — the sync test that pinned provider plugin.yamls to the Go `CredentialVars` now covers every extension kind: state backends, secret managers, routers, runtimes, and the simulator. Fixed drift it exposed: `states/dynamodb/plugin.yaml` was missing its `credentials:` block; the aws-sm / vault secret-manager plugin.yamls declared none (now surface `RUNFABRIC_SM_AWS_*` / `VAULT_*` with their per-request headers); cloudflare/ns1/azuretrafficmanager router plugin.yamls now declare their env fallbacks (new Go source `RouterPluginCredentialVars`, shipped as `routerPlugins` in the daemon-client contract); route53 is pinned to declare none (AWS default chain) and runtimes/simulator are pinned credential-free.
- **linode plugin.yaml apiVersion fixed** — was `runfabric/v1`, which discovery rejects; now the standard `runfabric.io/plugin/v1` (and it declares `LINODE_TOKEN`).
- **Schema: external provider IDs validate** — `provider.name` (and `providerOverrides.<key>.name`) now accept any installed external provider plugin ID via an `anyOf` alongside the built-in enum; previously a config naming an external provider (e.g. `linode`) failed schema validation even though the engine deploys it. The legacy `state:` block is now explicitly documented as legacy (local/postgres/s3 only) with `backend.kind` / `extensions.statePlugin` as the preferred selectors.
- **Examples and docs** — All example paths normalized to `examples/node/...` (e.g. `examples/node/hello-http/`, `examples/node/compose-contracts/`). [QUICKSTART.md](docs/QUICKSTART.md), [PROVIDER_SETUP.md](docs/PROVIDER_SETUP.md), and [examples/README.md](examples/README.md) updated with correct paths and quick-run commands.
- [FILE_STRUCTURE.md](docs/FILE_STRUCTURE.md) and [LAYOUT.md](docs/LAYOUT.md) updated to match current repo (engine, packages, schemas, bin, examples).

## [0.1.0-beta.0] - 2026-03-11

### Added

- Initial multi-provider framework scaffold.
- Provider adapters for AWS, GCP, Azure, Cloudflare, Vercel, Netlify, Alibaba FC, DigitalOcean Functions, Fly Machines, and IBM OpenWhisk.
- Stage-aware planning/build/deploy flow.
- Credential schema checks via `runfabric doctor`.
- Lifecycle hooks (`beforeBuild`, `afterBuild`, `beforeDeploy`, `afterDeploy`).
- Compose orchestration command with cross-service endpoint output sharing.
- Function lifecycle commands (`package`, `deploy function`, `remove`).
- Capability matrix sync automation.
- `runfabric init` starter templates: `api`, `worker`, `queue`, `cron`.
- Release automation workflow with ordered publish and tag/release creation.
- Signed release notes verification scripts and `release-notes/` structure.
- Docs consolidated under `docs/` (COMMAND_REFERENCE, README index).
- Compose contracts reference example under `examples/node/compose-contracts/`.

### Changed

- Project identity standardized as `runfabric`.
- Local artifacts/state paths standardized under `.runfabric/`.
- Provider adapters now expose consistent `invoke`, `logs`, and `destroy` behavior.
- Provider deploy flow supports optional command/API-backed real mode parsing.
- Deploy workflow supports optional rollback-on-failure semantics.

### Notes

- Configuration and environment variable naming are runfabric-only.
